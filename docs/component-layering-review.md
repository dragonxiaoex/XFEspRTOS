# xf_common 分层说明与改造记录

更新日期：2026-09-15。本页已按最终确认的范围更新，描述当前实现。

## 1. 本次采用的边界

**公共组件隔离厂商 SDK，FreeRTOS 作为共同系统接口直接使用，各平台维护自己的构建环境。**

- adapter 定义自有接口、配置、事件、句柄和错误码，厂商 SDK 调用放在适配实现中。
- 应用调用 adapter 获取平台能力，可以直接调用 FreeRTOS、标准库和其他公共组件。
- 协议负责字节流中的帧校验与编解码，产品负责命令含义和执行。
- 不封装 FreeRTOS，不改变 tick 单位，不新增 OS 接口；本轮不调整 CMake、组件目标或目录结构。
- 日志继续使用 `printf`，`XF_LOG_ENABLE` 仍在各产品的 `xf_project_config.h` 中设置。

这是源码接口的分层。当前 CMake 仍把 UART、协议、工具组织为一个 `common` 组件，产品头文件目录也仍由现有构建提供；本轮没有宣称完成构建依赖隔离。

## 2. ref 可以借鉴的设计

参考代码有五个文件：

| 文件 | 职责 | 本仓库沿用的原则 |
| --- | --- | --- |
| [sonoff_wifi_type.h](../ref/sonoff_wifi_type.h) | 自有 Wi-Fi 配置、模式和事件数据 | 对外使用自己定义的类型 |
| [sonoff_wifi_adapter.h](../ref/sonoff_wifi_adapter.h) | 适配接口与错误约定 | 接口说明输入、输出、失败与生命周期 |
| [sonoff_wifi_adapter.c](../ref/sonoff_wifi_adapter.c) | BK SDK 调用及参数、状态、事件转换 | 厂商差异集中在实现文件 |
| [sonoff_wifi.h](../ref/sonoff_wifi.h) | Wi-Fi 业务接口和回调约定 | 异步请求被接受与操作完成是不同结果 |
| [sonoff_wifi.c](../ref/sonoff_wifi.c) | 连接、扫描等业务流程和状态管理 | 适配层提供能力，应用层安排流程 |

值得沿用的细节：

- SDK 错误、连接状态等在适配边界转换，不要求业务判断厂商常量。
- 事件跨任务传递时复制必要数据，避免把 SDK 回调中的临时指针保存到队列外继续使用。
- 状态有明确归属，业务回调在状态锁外调用。
- 不支持的操作明确返回错误，例如参考中的反初始化接口。

参考管理层直接使用 FreeRTOS，符合本仓库确定的系统前提。其 Wi-Fi 任务、队列和状态机服务于异步连接流程，简单 UART、CRC 不需要照搬这些结构。

参考仍有需要按产品场景处理的事项：适配回调应明确任务/中断上下文和数据寿命；事件队列满时要保证业务能恢复；适配层使用的 SDK 内部接口需要随 SDK 维护。本轮只借鉴分层方式，没有复制 Wi-Fi 功能或修改 `ref`，也没有进行 BK 平台运行验证。

## 3. 当前公共代码的职责

保留现有文件位置，通过接口约束划分职责：

```text
xf_common/
├── main/entry.c                          # ESP-IDF 启动胶水，调用产品启动
└── components/common/
    ├── bsp/
    │   ├── xf_uart_bsp.h                 # UART 适配接口
    │   └── xf_uart_bsp.c                 # ESP-IDF UART 实现
    ├── protocol/
    │   ├── xf_mcu_protocol.h             # 协议上下文和编解码接口
    │   └── xf_mcu_protocol.c             # 帧头、长度、CRC、命令查找
    ├── utils/
    │   ├── xf_error.h                    # 自有错误码
    │   ├── xf_log.h                      # 日志宏，当前使用 printf
    │   ├── xf_utils.h / xf_utils.c       # CRC 等纯工具
    │   └── xf_task_com_def.h             # 保留现有 FreeRTOS 任务定义
    └── private/xf_private_device.h       # 产品启动约定
```

`bsp` 中的 UART 现在承担 adapter 职责，不需要仅为改名移动文件。以后有第二个平台时，保留公开头文件，为其提供另一份实现，由那个平台的构建选择。当前没有运行期切换平台的需求，直接使用普通函数。

`entry.c` 是启动组合点，可以调用产品启动。协议与纯工具没有产品依赖。LVGL 属于第三方代码，不重写其内部实现。

## 4. UART 已完成的修改

| 改造前 | 当前实现 |
| --- | --- |
| 公开 `uart_port_t` 和 `esp_err_t` | 初始化传板级整数编号，后续通过 `xf_uart_handle_t` 操作；状态使用 `xf_err_t` |
| 应用持有 SDK 事件队列和 `uart_event_t` | 队列留在实现中，`xf_uart_wait_event()` 返回 `xf_uart_event_t` |
| 产品直接查询或清空 SDK 缓冲 | 使用 `xf_uart_get_rx_length()`、`xf_uart_flush_input()` |
| 等待发送完成需直接调用 SDK | 使用 `xf_uart_wait_tx_done()` |
| 任务和时间单位使用 FreeRTOS | 保持 FreeRTOS 任务、`TickType_t`、`portMAX_DELAY` 用法 |

SDK 仍负责中断、收发环形缓冲和事件队列。每个适配句柄只保存串口号及 SDK 队列句柄，不维护另一套收发缓冲，也不创建额外 UART 任务。

当前串口能力为普通 UART、8N1、无硬件流控，不包含 LP UART。配置归产品所有；通用协议无需知道 GPIO 或串口编号。

XC200 的接收任务仍是“等待事件 → 读取字节 → 协议解析 → 执行产品命令”。公开 API、返回值和原有调用点已同步修改。详见 [UART 模块说明](uart.md)。

## 5. 协议已完成的修改

### 独立命令表上下文

删除全局可变命令表和只有一种实现的驱动函数表，使用 `xf_mcu_protocol_t` 加普通函数。每个上下文借用自己的只读命令表，初始化不分配内存、也不复制表。

命令表应使用紧凑列表，无需按命令编号下标排列；表及其内容在上下文使用期间必须有效且不变。初始化不能与该实例的编解码并发，只读编解码可使用独立输入输出缓冲并发执行。

产品的眼睛位置、显示模式等业务仍在 XC200 中，协议模块仅返回命令编号和负载。

### 明确容量与失败语义

| 接口 | 当前约定 |
| --- | --- |
| `xf_mcu_protocol_init()` | 校验数量、命令编号、名称和负载长度，拒绝重复项；失败不改变上下文 |
| `xf_mcu_protocol_input_check()` | 输入容量、有效长度、起点及输出容量分开传入；只复制第一帧的命令体 |
| `xf_mcu_protocol_parse()` | 先校验完整长度、功能码、CRC、命令和输出容量，再复制负载 |
| `xf_mcu_protocol_pack()` | 替代旧 `reverse()`；先检查负载长度和完整帧容量，再写输出 |

修复的原有问题包括：解析时忽略调用者输出容量、打包只检查最小 8 字节容量、193 项私有命令导致全局数组越界，以及拆包时不明确单帧输出大小的问题。

当前私有命令最多 192 项，编号范围 `0x40`～`0xFF`，每项名称非空且以零结尾。`len == 0` 表示可变负载长度，非零表示固定长度并在打包和解析时检查。

帧最大 2048 字节，负载最大 2040 字节。线上帧格式、字节序及 CRC 算法保留原定义：

```text
55 AA | function:1 | command:1 | payload_length:2 (小端) | payload:N | CRC:2 (小端)
```

CRC 从 command 开始覆盖 command、长度和负载。设置帧功能码为 1，查询帧为 2。

编解码失败不修改输出数组或实际输出长度。`input_check()` 的 `pass` 在未通过校验时为 0，只有 `pass > 0` 时输出命令体有效；返回 -1 时调用者必须处理错误，不能原样无限重试。

协议现在只依赖标准库和 CRC，无需 UART、FreeRTOS、日志或产品配置就能独立编译。

## 6. 日志配置与纯工具

公共日志改为包含稳定的配置接口 `xf_log_config.h`。每个产品提供同名配置适配头，当前两个产品的适配头均包含自己的 `xf_project_config.h`，因此开关继续只在原位置维护。

```text
xf_log.h → 产品提供的 xf_log_config.h → xf_project_config.h 中的 XF_LOG_ENABLE
```

公共日志仍需要宿主提供配置，但不再硬编码产品配置文件名。移植时可提供一个只定义 `XF_LOG_ENABLE` 的配置头；主机测试就是这样使用的。当前产品包含路径由现有 CMake 提供，本轮没有新增构建宏或生成步骤。

`printf` 后端及控制台路由保持现有行为，不接入业务 UART、不新增异步日志队列。关闭日志时不计算日志参数。CRC 保持纯工具实现，清理了无用包含和历史注释代码；启动入口只保留实际需要的包含。

## 7. 后续公共组件按什么规则编写

1. 先定义平台能力的自有接口，公开头文件不包含厂商 SDK；可以直接包含 FreeRTOS。
2. SDK 参数、事件与错误只在适配实现中转换，函数注释明确超时单位、所有权、调用上下文和释放顺序。
3. 管理层安排业务流程；协议、算法可以直接作为纯组件被调用，不为其添加无意义的 adapter。
4. GPIO、UART 编号、屏幕型号、业务命令等配置由产品提供，公共组件不判断 `xc100` / `xc200`。
5. 有异步流程才使用任务和队列，已有驱动缓冲能满足需求就直接复用。

本轮范围是现有公共框架及其必要调用点，XC200 的 LCD/LVGL 等产品代码仍存在直接 SDK 调用。以后将这些功能提取成公共组件时，再把其平台接入放进对应 adapter。

## 8. 验证

以下命令用于本次验证：

```sh
python3 tests/common/run_tests.py
python3 xf_tool/build.py MODEL=xc100
python3 xf_tool/build.py MODEL=xc200
```

主机测试使用实际协议、CRC、UART 适配实现及 XC200 收包代码；只替换 SDK/FreeRTOS 运行环境。覆盖协议边界、命令表、全部合法负载长度、多实例隔离、环形缓冲回绕、拆包粘包、串口错误恢复、初始化失败清理和日志开关。公开头文件另在不提供厂商 SDK / 产品头的环境中编译。

主机测试开启 AddressSanitizer 和 UndefinedBehaviorSanitizer，受运行环境限制关闭 LeakSanitizer。详情见 [测试说明](../tests/common/README.md)。XC100 / ESP32-P4 和 XC200 / ESP32-S3 均完成构建；未进行板上烧录和压力测试。XC200 的串口协议启动调用仍保留原来的注释状态。
